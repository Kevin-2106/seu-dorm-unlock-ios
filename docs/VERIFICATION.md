## 配置码：可以导入，但似乎会失效

**现象**：在一台设备「导出配置码」，在另一台设备「从剪贴板导入」，导入本身成功，但之后拿这份凭据开门似乎会失效。

**推测（未验证）**：NFC 每次开门成功后，锁会返回一把**新的 chainKey** 并换掉旧的（密钥轮换）。导出的配置码里装的是导出那一刻的钥匙：

- 如果导出之后，原设备又用 NFC 开过门，锁里的钥匙已经换了，配置码里的就是旧钥匙；
- 蓝牙路径下，锁返回错误码 `27` 时也会要求换钥匙。

两台设备共用同一份凭据，其中一台开过门，另一台手里的就可能是旧的。

**没有查实的部分**：具体是哪一种情况、服务器那边的凭据是否同步更新、导入后第一次开门返回的是什么错误码——都没有抓到。如果你遇到了，欢迎开 issue 附上状态卡片里的错误码。

**建议**：

- 把配置码当作**备用 / 一次性迁移**，不要指望两台设备长期共用同一份；
- 失效后，在那台设备上重新「登录并拉取门锁凭证」即可恢复（⚠️ 登录会把官方 App 顶下线）。

## 凭据自动刷新：逻辑在，但没触发过

移植自上游的恢复流程：

| 锁返回 | 含义 | 处理 |
|---|---|---|
| `25` | 离线次数用完 | 用已登录的会话重新拉取凭据，保存后自动重试整套开门流程 |
| `24` | 凭据过期 | 没登录则先用 Keychain 里保存的账号密码自动登录，再拉取、重试 |
| `27` | 门已开，但锁要求换钥匙 | 通过蓝牙 `0x76` / `0x77` 向锁索取新 chainKey 并保存 |

代码在 `ios/DoorUnlock/Sources/DoorUnlock/DoorBLEManager.swift`。实测过的只有"直接开门成功"这条路，上面三条分支没有在真机上被触发过，所以标为未验证。
